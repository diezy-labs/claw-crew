## 19. MVP Strategy
## 19.1 Product scope reality

The complete Fleet world can support Developer, Marketing, Content, Research, Operations, and many other Ship Charters. A solo founder must not build all of them simultaneously.

The product core may be horizontal:

```text
Fleet + Quartermaster + Ship + Navigator + Squad + Crew
+ Quest + Map + Artifact + Learning + Approval
```

But the first go-to-market pack must be vertical and opinionated.
## 19.2 Recommended MVP

```text
Quartermaster Office
+ Mission Board
+ One Developer Delivery Ship
+ One Navigator
+ Three persistent Crew Specialists
+ Two Artifact contracts
+ One safe approval-gated external action
+ BYOK / BYOM onboarding
+ Local-first storage and basic Treasury/Logbook
```

### MVP Crew

| Crew Member | Primary Artifact |
|---|---|
| Repository Analyst | Repository Health Brief |
| Engineering Planner | Engineering Plan & Risk Brief |
| QA/Risk Reviewer | Validation & Risk Review |

### MVP Quest flow

```text
Owner objective
→ Quartermaster intake
→ Mission Board Quest
→ Navigator Map
→ Repository analysis
→ Engineering planning
→ QA/risk review
→ Quartermaster executive briefing
→ Owner review
→ proposed memory rule
```

### MVP external action

```text
Create GitHub issue draft after Captain’s Approval.
```

No merge, deployment, external publishing, secret rotation, destructive action, or universal tool authority in MVP.
## 19.3 Phased roadmap

| Phase | Scope |
|---|---|
| Phase 1 | Quartermaster direct interaction, first Ship, three Crew, first Artifact |
| Phase 2 | Mission Board, Map, Ship Report, Treasury, Logbook, feedback-to-memory |
| Phase 3 | CI triage, release readiness, schedule/webhook trigger, GitHub draft issue approval |
| Phase 4 | Full five-member Developer Ship, Charter/versioning/export, temporary agent promotion |
| Phase 5 | Pro multi-Ship capacity, curated Charter packs, backup/export, consultant workflows |
| Phase 6 | Team shared Ships, approvals, shared memory, roles, audit search |
| Phase 7 | Private Dockyard/business support only after repeatable demand |

## 20. Metrics
## 20.1 North-star metric

> **Verified Useful Treasures per Active Ship per Week**

A Treasure qualifies when:

1. A Quest/Voyage completes without material policy violation.
2. The Artifact is accepted by Owner or accepted through explicit policy.
3. The outcome is useful, evidenced, or leads to a valid decision/action.
4. Cost stays within budget.
5. No major corrective incident is created.
## 20.2 Product metrics

| Category | Metric |
|---|---|
| Activation | Time to first useful Artifact; time to first Treasure |
| Setup | Provider connection success; Ship activation rate; Charter completion rate |
| Usage | Weekly active Ships; Voyages per Ship; active Quest rate |
| Quality | Artifact acceptance rate; revision rate; evidence completeness; reviewer agreement |
| Learning | Feedback-to-memory proposal rate; memory confirmation rate; rule rollback rate |
| Trust | Approval rate; rejection rate; policy-denied action rate; emergency stop usage |

| Retention | Weekly active Ship retention; recurring Quest usage; Charter reuse rate |
| Growth | Artifact export/share rate; Charter import/export rate; contributor PRs/issues |

## 22. Final Decisions

1. The product is a **local-first, self-hosted AI organization workspace**, not merely an agent runtime or chatbot.
2. The user is the **Pirate King / Owner** with final authority.
3. Quartermaster is the **AI CEO / Executive Orchestrator**: broad awareness and coordination authority, limited direct execution authority.
4. The **Fleet/Dermaga** is the organization and operations hub.
5. The **Mission Board** is the global source of Quest work, prioritization, and routing.
6. A **Ship** is a persistent operational home for a specialist AI team, not a Workspace or Project.
7. A **Navigator** leads execution at Ship level: Quest intake, Map creation, delegation, Artifact collection, and Ship reporting.
8. A **Squad** is a functional team inside a Ship; Crew Members are persistent specialists.
9. A **Quest** is a living SOP/workflow/objective; a **Map** is its execution plan; a **Voyage** is one run.
10. **Artifacts** are reviewable evidence/deliverables; **Discoveries** are important findings; **Treasures** are validated outcomes.
11. The primary differentiation is **Artifact-Driven Persistent Collaboration**, not generic multi-agent spawning.
12. The product is BYOK/BYOM/BYOI-friendly: user chooses intelligence, infrastructure, and provider relationship.
13. Community restricts active persistent AI capacity—not the user’s ability to organize Workspaces, Projects, Maps, or Quests.
14. Monetization sells expansion, Charters, maintenance, collaboration, support, and deployment—not platform model credits.
15. Gamification should improve clarity, progress, ownership, and delight; it must never become manipulative or hide professional meaning.
16. MVP begins with one production-ready **Developer Delivery Ship**, not every industry/function at once.
