## 4. Design Principles

## 4.1 Calm command, not pirate cosplay

Use maritime language as a meaningful layer over real product entities:

```text
Quartermaster = executive orchestrator
Mission Board = global work queue
Ship = persistent specialist team container
Navigator = Ship-level planner
Quest = SOP/workflow/objective
Map = execution plan
Voyage = run
Artifact = deliverable/evidence
Treasure = approved/validated value
Treasury = provider cost/budget
Logbook = audit/activity history
Fleet Code = policy and permission rules
Crow’s Nest = health/technical monitoring
```

Every non-obvious narrative label must have a functional subtitle in high-stakes contexts:

```text
Treasury
Provider Cost & Budget

Captain’s Approval
Review external actions before they run

Logbook
Audit & Activity History

Fleet Code
Policies, permissions, and safety rules
```

## 4.2 Outcome before configuration

Default entry question:

```text
What should your Fleet accomplish next?
```

Not:

```text
Which provider, agent, MCP tool, cron syntax, model parameter,
or workflow graph do you want to configure?
```

## 4.3 Conversation is universal; structure is durable

Quartermaster chat handles all ad-hoc interaction. Important conversations must be promotable into structured work:

```text
[Save as Artifact]
[Create Quest]
[Send to Mission Board]
[Assign to Ship]
[Remember as a rule]
[Request approval]
```

## 4.4 Artifacts are the work product

Chat messages are ephemeral. Artifact is durable.

Every significant work path must end with a viewable artifact, evidence bundle, decision brief, checklist, draft, report, or approved outcome.

## 4.5 Advanced capability is earned, never buried

Use progressive disclosure:

```text
Simple action
→ relevant summary
→ “Advanced controls” affordance
→ dedicated technical surface
```

A developer should reach logs, model parameters, tool scope, raw run traces, or configuration in one to two navigational steps—not through hidden tricks.

## 4.6 Human command is visible

Every external or high-impact action must show:

- What will happen.
- Where it will happen.
- Why it is proposed.
- Which Ship/Crew produced the proposal.
- Evidence/source links.
- Provider/model/cost estimate where relevant.
- Approve, edit, reject, or pause controls.
